# resolved v0

`resolved` is the userspace DNS resolver configuration service for SunlightOS. It owns the system DNS server list and search domains, and exposes a classic `/etc/resolv.conf` compatibility view.

## Goals (v0)

- Central owner of DNS configuration state.
- `/etc/resolv.conf` is a generated facade, not the source of truth.
- `networkd` can hand DHCP/static DNS servers to `resolved`.
- Small CLI (`resolvectl`) for inspection and simple admin.
- Preserve working DNS/TLS/fetch behavior.
- No kernel changes.
- Tiny memory and no large dependencies.
- Degrade gracefully if `resolved` is unavailable.

Non-goals for v0: DoT, DoH, split-DNS, caching (net_server keeps its cache), full enterprise features.

## Default policy

Order of precedence for effective servers:

1. Manual (user `resolvectl set ...`) — highest, sticks until cleared or `default` used.
2. DHCP/Static from `networkd` (marked `Dhcp` or `Static` with interface).
3. System default (OpenDNS for v0):

   ```
   208.67.222.222
   208.67.220.220
   ```

Emergency fallback in resolution paths remains simple and explicit.

## IPC (registered as "resolved")

Core ops (compact register IPC):

- `GET_CONFIG`
- `GET_SERVER <index>`
- `SET_SERVERS <addr...>` (sets Manual)
- `ADD_SERVER <addr> <source_tag>`
- `CLEAR_SERVERS`
- `USE_SYSTEM_DEFAULT`
- `UPDATE_FROM_NETWORKD <iface_packed> <dns...>` (from networkd)
- `RENDER_RESOLV_CONF`
- `RESOLVE_NAME` (stub in v0; real resolution stays in net)
- `FLUSH_CACHE` (stub)

Replies use `ResolvedMsg::REPLY`. Errors use `ResolvedMsg::ERROR`.

See `ipc/src/lib.rs`: `ResolvedMsg`, `DnsSource`, `DnsServerSummary`, pack/unpack helpers.

## CLI: resolvectl

```
resolvectl status
resolvectl servers
resolvectl set 208.67.222.222 208.67.220.220
resolvectl default
resolvectl render
resolvectl query <name>   # v0 note: delegates to net
resolvectl flush-cache
resolvectl json
```

Example (no DHCP DNS yet):

```
DNS Servers:
  208.67.222.222   SystemDefault
  208.67.220.220   SystemDefault

resolv.conf:
  /etc/resolv.conf generated
```

With DHCP DNS from networkd:

```
DNS Servers:
  10.0.2.3   Dhcp eth0
```

## /etc/resolv.conf

- Generated on open by vfs_server from `resolved` state (via `RENDER_RESOLV_CONF`).
- Created as a dynamic ramfs entry; root remains read-mostly.
- Normal processes see a read-only generated file.
- Only `resolved` (and privileged internal vfs paths) control content.
- Direct user writes are not supported in v0 (will be denied or ignored).

Example generated content:

```
# Generated by SunlightOS resolved.
# Do not edit this file directly unless you know what you are doing.
nameserver 208.67.222.222
nameserver 208.67.220.220
```

## Integration with networkd

- `networkd` calls `UPDATE_FROM_NETWORKD` (best effort) when it learns DNS via:
  - `ingest_live_from_net` (from `net` GETIP)
  - `SET_STATIC_IPV4` with `dns ...`
- If `resolved` is absent, networkd logs nothing (or a debug) and continues.
- `networkctl status eth0` continues to show its own `dns:` field for convenience.

## Fetch / net resolution behavior

`fetch`, TLS, and other users call `net` (NetOp::RESOLVE). `net_server`:

- Keeps its resolver chain (hosts → cache → upstream UDP).
- At startup and on local-miss before upstream query, does a best-effort refresh of `chain.upstream` from `resolved`.
- If `resolved` is unavailable, the previous working upstream (QEMU slirp, ingested, or built-in fallback) is retained.
- Existing successful `fetch https://archlinux.org` behavior is preserved.

## Write policy (v0)

- `/etc/resolv.conf` is effectively read-only to unprivileged processes.
- `resolved` manages state; vfs_server materializes a view on demand.
- Future (documented, not implemented):
  - Resolver-management capability/token for approved writers (VPN, Cisco clients, etc.).
  - VFS write hook that can translate approved direct writes into resolved API calls.
  - Per-interface and search-domain expansion.

## Persistence

v0 is in-memory only. Later can persist via `sunlight-kv` / StateFS / sm if desired.

## Validation

```
cargo check
cargo check -p sunlight-resolved
cargo check -p sunlight-networkd
cargo check -p sunlight-vfs-server
cargo check -p sunlight-net-server
```

Boot checks:

```
networkctl list
networkctl status eth0
resolvectl status
resolvectl render
cat /etc/resolv.conf
fetch https://archlinux.org
```

Expected:

- `resolvectl status` lists current servers with sources.
- `/etc/resolv.conf` exists and contains `nameserver` lines.
- If no DHCP DNS, OpenDNS appears.
- `fetch` resolves and downloads successfully.
- Root FS not made broadly writable.
- Services boot in either order (resolved before/after networkd) without breakage.

This is the foundation for future resolver features while keeping v0 small and reliable.
