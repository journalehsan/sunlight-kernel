# Ensoniq AudioPCI ES1371

SunlightOS recognizes PCI `1274:1371` and keeps it inside the existing
`audiod`/`sunlight-audio` playback contract. `audiod` probes ES1371 before the
existing Intel HD Audio backend, so an ES1371 controller is selected
deterministically when present while VirtIO and HDA remain available as
fallbacks.

The kernel owns PCI configuration and validates BAR0 as an I/O BAR. The probe
temporarily disables only PCI I/O decoding and bus mastering while sizing the
BAR, restores the original BAR, then enables those two bits while preserving
all unrelated command bits. The userspace grant is limited to the discovered
port range and is available only to the `audiod` process. DMA comes from the
existing physically contiguous, page-aligned `dma_alloc` grant; the ES1371
programmed address is the returned physical address, never the userspace
virtual address.

The backend performs bounded controller reset, keeps the ES1371 memory bus
request enable asserted while leaving control test bits clear, performs AC'97 warm reset, codec volume
unmute for master/PCM paths, the ES1371 sample-rate-converter setup for 48 kHz,
and signed 16-bit stereo Playback 2 configuration. It uses the same 4 KiB
period size and bounded ring ownership model as the HDA backend. `audiod`
continues to own mixing, volume policy, system sounds, stream ownership, stop,
and cleanup. The DAC2 hardware period count is programmed during stream setup;
period refills only copy PCM and advance software ownership, preserving the
hardware playback cursor.

Device Manager receives the normal PCI inventory record and identifies the
device as **Ensoniq AudioPCI ES1371**, class **Audio devices**, driver
**ES1371/audiod**, bus **PCI**, and vendor/device **1274:1371**. The record is
published as Active only after ES1371 initialization and backend registration
succeed; initialization failure is reported as Probe failed. `deviced` refreshes
the kernel inventory for inventory queries, so a late audio-service bind is
visible without restarting Device Manager. `audiod` also retries discovery
when PCI enumeration has not completed yet; it does not repeatedly allocate
DMA after a controller has already been found and failed initialization.

The current kernel exposes user drivers with polling endpoints for device I/O;
its generic user IRQ registration path currently covers keyboard and mouse,
not PCI audio. The backend enables the ES1371 Playback 2 period interrupt
source and acknowledges each completion from the bounded polling pump: it
reads STATUS, clears only `P2_INT_EN`, then restores the cached SERIAL value.
That acknowledgement is required even when no userspace IRQ wait endpoint is
claimed; VMware otherwise advances one 4 KiB period and then holds the DMA
cursor at the boundary. The reported PCI IRQ remains visible in Device
Manager. Capture,
MIDI, joystick, SPDIF, suspend/resume, and alternate PCM formats are outside
this phase.

Host tests cover BAR interpretation and rejection of invalid I/O resources.
Compilation and host tests do not establish playback in VMware. The isolated
VMware ES1371 audit now verifies the acknowledgement path: DMA advanced from
1,024 to 81,920 frames, completion acknowledgements increased from 1 to 80,
and the injected 440 Hz test tone completed. Human-audible output still needs
separate host capture or listening evidence.
