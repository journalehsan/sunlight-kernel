# STACK-1: Demand-backed main user stacks

**PARTIAL qualification.** The opt-in prototype saved 15,908 private stack frames (62.14 MiB) at the matched 32-leader document-idle checkpoint. All four demand guests and their eager controls passed the bounded compressed boot and interactive TLS gate. The prototype remains off by default.

Enable kernel feature `demand_main_stack` for the early native init, VFS and TTY stacks and the native spawn/exec image builder. Linux personality images, worker stack allocation, and kernel stacks retain their existing paths. The ordinary eager stack helper still maps all 512 pages. The native startup writer retains its ABI: checked seed sizing covers argv, envp, pointer tables, AT_RANDOM, alignment and red-zone slack, with a four-page minimum. Raw boot entry seeds four pages and keeps its original stack pointer.

The ledger reserves the original 2 MiB window and one separate protected, unmapped page on either side. A collision rejects demand image admission. The user fault path accepts only ring-3 non-present data reads and writes; it checks the active CR3 against the current VM identity and resolves the owner in that same generation. Growth requires the exact protected stack reservation, matching owner and generation, and RW permission. A swapped or otherwise occupied non-present leaf is never overwritten. Checked kernel reads and writes can populate individual reserved pages through the same ledger authorization during the existing serialized user-copy walk. Native signal trampoline writes use that checked copy path; dedicated signal delivery tests were not run.

Backing is sparse. A large adjustment can touch any usable page, including the lowest one, without committing the intervening pages. A touch to either guard cannot extend the stack. A guard does not trap a register adjustment or a jump over it into a separate valid mapping; arbitrary stack-clash prevention and compiler probe coverage are outside this qualification.

The unpublished image prepares both leaf-table paths. A live growth operation can only install a leaf in an existing table. Scheduler serialization and the PMM lock make lookup, owner charge, zeroing and publication one operation. A second fault finding the valid leaf can retry after local invalidation without another charge. Runtime PMM failure leaves the leaf absent; the ordinary terminal fault path or checked-copy error remains in effect. A copy spanning several pages can leave earlier valid commitments in place if a later page fails. Failed image staging and retired VMs reclaim the user page-table graph using the existing lifecycle paths. Stack leaves are private frames and do not enter the anonymous ZRAM candidate set. Virgin absent pages consume neither a private frame nor a ZRAM slot; reclaiming committed stack pages during process lifetime is unsupported.

TLS overlap saved 17,917 private frames (69.99 MiB) at the matched 36-leader checkpoint. These are gross leaf-frame savings; PMM low water includes all classes and is measured from boot through the overlap checkpoint. `sunlightd` reached 154 resident pages and an accessed depth of 154 pages in all demand runs. That is a 616 KiB page span, not a witness of user execution beyond 616 KiB. The TSC measurements cover the successful demand handler from entry through local invalidation, including scheduler and PMM lock time, and exclude entry/return overhead and kernel-copy commitments. They are same-vCPU TSC deltas under TCG, not a hardware latency prediction. Eager controls had zero such handler samples.

All pairs used fresh diskless QEMU 11.1.3 TCG guests with two vCPUs, the same compressed resource archive and compressed VFS executable, and the same workload runner. Evidence includes the VFS 2 KiB shared boot read, document workload and recovery, interactive TTY and CA installation, and two simultaneously live verified TLS sessions whose distinct payloads were read back and whose sessions closed. The first development image failed the ledger/PTE invariant during boot; the corrected image accounts for absent stack leaves and guard reservations. The [machine-readable results](demand-backed-main-user-stacks-results.json) record that failure separately.

The host ledger check passed. The opt-in native kernel fixture exercises unpublished VMs with the real PMM and page tables. It verified startup contents and alignment with a 17 KiB argument, injected admission failures, fault backing OOM, repeated commit attempts, zero fill, NX leaf flags, bound checks, and repeated reclamation to the starting PMM free-frame count. The fixture committed pages at 720 KiB depth and at the bottom of the window. This is direct kernel-path evidence, not a ring-3 deep-stack or negative fault test or an SMP collision witness. The normal TLS runs separately show repeated `fetch` process reaping; they do not isolate every VM retirement interleaving.

To reproduce the matrix, build release kernels with `main_stack_census,native_document_viewer`, adding `demand_main_stack` to the experimental kernel. Set `SUNLIGHT_BOOT_RESOURCE_VFS` to the compressed-resource VFS executable, and package with `SUNLIGHT_BOOT_RESOURCE_MODULE` and `tools/make_hybrid_iso.sh`. Run `tools/network_tls_gate.py --compressed-boot --heap-overlap --tcg --cpus 2` with the respective ISO, RAM size and firmware (add `--uefi` for that guest). Build additionally with `main_stack_test` for the boot fixture and supply a guest entropy device (`-device virtio-rng-pci`). Run the host test with `rustc --edition=2021 --test tools/tests/main_stack_ledger.rs` and execute the resulting binary. The evidence paths are under `target/stack-1`.

Helios worker stacks, arbitrary fault recovery, forced concurrent same-leaf faults, ring-3 guard and execute rejection, and sustained 512 MiB operation are not qualified. Compressed resources remain opt-in; this work does not change the heap sizes, anonymous mmap policy, ZRAM reclaim policy or VFS migration prerequisites.
