# Native C guest-to-host TCP acceptance (2026-11-12)

Fresh evidence for the external-path milestone. The loopback evidence remains
in `../results-2026-11-12-native-net/`; this directory is separate and does not
reclassify loopback as an external pass.

## Topology

`tools/native-c/guest.py --net` boots one disposable QEMU TCG guest with
`-m 2048M`, `-smp {2,4}`, `-netdev user,id=net0`,
`virtio-net-pci,netdev=net0,disable-modern=on`, and a QEMU `filter-dump`
pcap. The backend is QEMU user-mode networking (slirp); no `hostfwd` is used.

The guest's own DHCP log records:

```
[DHCP] lease acquired address=10.0.2.15/24 gateway=10.0.2.2 dns=10.0.2.3
```

QEMU's user-mode backend exposes the host loopback as the gateway/host alias
`10.0.2.2`. The host peer therefore binds `127.0.0.1:0` only; slirp forwards
the guest's connection to `10.0.2.2:<port>` to that listener. The host peer
observes a slirp-side `127.0.0.1:<ephemeral>` peer, not the guest address.

Data path:

```
native C client -> sunlight-libc net_bridge -> NetOp IPC
  -> production net_server smoltcp TCP -> ProxyNetDevice
  -> kernel frame proxy -> virtio-net -> QEMU slirp
  -> host 127.0.0.1 listener -> return path
```

## Commands

All commands were run from the repository root. The orchestrator builds the
native archive, compiles the requested client, starts the host peer, waits for
its explicit `HOST-PEER READY` line, then starts the guest.

```sh
python3 tools/native-c/run_external_tcp.py --mode echo --cpus 2 \
  --out target/netexternal-echo-2cpu-v2 --timeout 300 \
  --run-id external-echo-2cpu-v2
python3 tools/native-c/run_external_tcp.py --mode echo --cpus 4 \
  --out target/netexternal-echo-4cpu-v2 --timeout 300 \
  --run-id external-echo-4cpu-v2
python3 tools/native-c/run_external_tcp.py --mode echo --cpus 2 \
  --out target/netexternal-echo-repeat-2cpu-v2 --timeout 300 \
  --run-id external-echo-repeat-2cpu-v2
python3 tools/native-c/run_external_tcp.py --mode stall --cpus 2 \
  --out target/netexternal-stall-2cpu-r2 --timeout 300 \
  --run-id external-stall-2cpu-r2
python3 tools/native-c/run_external_tcp.py --mode stall --cpus 4 \
  --out target/netexternal-stall-4cpu-r2 --timeout 300 \
  --run-id external-stall-4cpu-r2
```

The host peer is `tools/native-c/tcp_host_peer.py`. It binds port 0, keeps the
listener open, prints `HOST-PEER READY mode=<mode> addr=127.0.0.1 port=<port>`,
then closes the listener immediately after accepting the guest connection.
Closing after accept makes the client's later connect to the same port a
deterministic refusal. The peer validates every length-prefixed frame against
the expected deterministic payload, echoes the header and payload byte-for-byte,
handles partial reads/writes, recognizes the zero-length terminator, and uses
bounded socket timeouts. `echo` exchanges five frames; `stall` reads one frame
and withholds every response.

## Successful external exchanges

Wire payloads: sizes 1, 7, 64, 255 and 1024 bytes, each with embedded NULs.
Each frame is a 4-byte big-endian length followed by the payload (4 bytes of
sequence + generated bytes). The zero-length frame terminates the session.

| --- | --- | --- | --- | --- |

| echo, 4 CPUs | `10.0.2.15 -> 10.0.2.2:44185` | `127.0.0.1:44185` | same PASS | same PASS |

| stall, 2 CPUs | `10.0.2.15 -> 10.0.2.2:34775` | `127.0.0.1:34775` | `PASS errno=110 elapsed_ms=10000 socket_live=0 listener_live=0 stream_live=0` | `PASS mode=stall received_frames=1 bytes=8` |
| stall, 4 CPUs | `10.0.2.15 -> 10.0.2.2:36315` | `127.0.0.1:36315` | same PASS | same PASS |

The echo client also reports the requested failure-path errno values:

```
tcp-echo: refused errno=111
tcp-echo: nonblocking-connect errno=95
```

`111` is `ECONNREFUSED`; `95` is the bridge's explicit `EOPNOTSUPP` for
asynchronous connect.

## Byte integrity and NIC capture

The primary evidence is endpoint byte equality, not packet counts.

| Run | outbound bytes | outbound SHA-256 | inbound bytes | inbound SHA-256 |
| --- | --- | --- | --- | --- |
| echo, 2 CPUs | 1395 | `47a9ea4aa44f1a4c6fab1982557cfea60efce87f55c49d9c41888a47e33e11bf` | 1391 | `acd17ec6a05c03d57191eb4a8e03b92b1aa18109134a30fbce50ad0accf5fd89` |
| echo, 4 CPUs | 1395 | same | 1391 | same |
| echo repeat, 2 CPUs | 1395 | same | 1391 | same |
| stall, 2 CPUs | 12 | `3e3c22af446e48578259d3857b8b22018326dc5dc92abb77f0823ae81e1a7822` | 0 | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |
| stall, 4 CPUs | 12 | same | 0 | same |

`1395` = five 4-byte headers + 1371 payload bytes + the 4-byte terminator.
`1391` = five echoed 4-byte headers + 1371 echoed payload bytes. The outbound
and inbound hashes matched the independently generated expectations exactly.

Each echo pcap contains 2 ARP frames (request for `10.0.2.2` and reply), 4 DHCP
UDP frames, and 35 TCP frames in the 4-CPU/repeat runs (38 in the 2-CPU run,
including three benign duplicate ACKs). The stall pcaps contain 2 ARP frames,
4 DHCP UDP frames, and 9 TCP frames. These are real NIC frames; unlike the
loopback run, TCP is present.

The minimal stdlib reader/reconstructor is `tools/native-c/pcap_tcp.py`
(`tshark`, `tcpdump` and `scapy` were unavailable in this environment). It
reassembles each TCP direction by sequence number and compares the resulting
stream to the expected framed bytes.

## Failures and limitations

- The first two stall orchestrations were marked `FAIL` only because the
  checker treated the absence of a host-to-guest payload flow as an error.
  The guest and host endpoint lines already passed. The corrected checker
  treats zero inbound payload bytes as the intended stall outcome; the
  first-attempt summaries are retained in `regressions/` for transparency.
- The host libc suite's parallel run hangs at
  `secret_store::tests::default_options_are_private_and_bounded` because that
  production test calls native `getuid`/`getgid` syscalls 35/36, which are
  Linux `nanosleep`/other syscalls. The retained log is
  `regressions/libc-host/known-parallel-hang.log`. The supported filtered run
  (`tools/native-c/tests/run_unistd.py`) passed 121 tests with the two
  credential-calling tests filtered.
- Only one host peer and the single `10.0.2.2` slirp alias are exercised.
  UDP, asynchronous connect, nonblocking accept, shutdown, readiness
  integration, dup/fork attachment transfer, bind-then-connect, socket
  options, SIGPIPE, IPv6 and DNS-resolved public endpoints remain unsupported
  or untested.
