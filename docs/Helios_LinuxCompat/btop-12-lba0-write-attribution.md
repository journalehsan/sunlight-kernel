# BTop-12: Attribute the LBA 0 write

The BTop-11 event was a successful guest-visible, 512-byte write at LBA 0.
The boot path accounts for it: Limine's legacy BIOS disk enumeration reads
sector zero and writes the same buffer back as part of optical-drive detection.
It occurs before the kernel fixture and is outside the authorized ranges.
The original raw write control remains failed.

## Original command and trace

The original full argv is in `target/btop-11/write/command.json` and
`target/btop-11/write-retry/command.json`. From the repository root, the
successful-boot retry's argv is equivalent to:

```sh
run="$PWD/target/btop-11/write-retry"
qemu-system-x86_64 -nodefaults -machine q35 -accel tcg -m 4096 -smp 4 \
  -cdrom "$PWD/target/btop-11/write.iso" -boot d -vga std -display none \
  -monitor none -serial "file:$run/serial.log" \
  -drive "id=fixture,file=$run/disposable.img,if=none,format=raw,cache=writeback" \
  -device virtio-blk-pci,disable-modern=on,ioeventfd=off,drive=fixture \
  -device virtio-rng-pci,disable-modern=on -nic none -no-reboot -no-shutdown \
  -trace enable=virtio_blk_handle_write -trace enable=virtio_blk_rw_complete \
  -trace enable=virtio_blk_req_complete
```

This is an evidence record, not a command to run on the preserved image.
The first run uses the sibling `write` directory and omits `-vga std`.
Both captures start at process launch, cover firmware and guest boot, and end
at QEMU's SIGTERM exit after the framebuffer panic or the READY marker.
The logs have no timestamps, read-submit events, explicit flush events, node
events, or guest request IDs. The original QEMU executable version was not
recorded in either trace; the paused check used the installed 11.1.3.

The original CLI graph is legacy VirtIO PCI → BlockBackend `fixture` →
raw → file protocol → the exclusive 4 MiB regular file, writable with
writeback caching. The ISO is a separate read-only CD-ROM. A paused QMP
check on the same retry topology confirms PCI 00:02.0, 1af4:1001,
`/machine/peripheral-anon/device[0]/virtio-backend` → raw `#block302`
→ file `#block293`; CD backend `ide2-cd0` → raw `#block149` → file
`#block069`. The autogenerated node names are from the paused check only.
The first run has a different PCI layout because VGA is omitted.

QEMU's `hw/block/virtio-blk.c` emits `virtio_blk_handle_write` on the
VirtIO OUT path with device pointer, request pointer, guest header sector,
and payload length in 512-byte sectors. QEMU converts that LBA to bytes
when submitting to the BlockBackend. The paired `virtio_blk_rw_complete`
reports the backend return code; `virtio_blk_req_complete` reports VirtIO
status. Both are zero for every row below. The event is a device-layer
payload submission, distinct from the separate FLUSH case. Raw maps these
logical ranges directly to backing-file offsets; the event itself is not
a host file write trace or evidence of persistence after power loss.

## Boot source and correlation

The first run records the legacy BIOS Limine handoff, then panics in
`kernel/src/main.rs:480` before the kernel initializes VirtIO block or
enters the fixture. Its trace still contains the same early LBA 0 write
and no writes at 62 or 63. Both runs have three VirtIO read/write completion
pairs followed by the LBA 0 submission and completion at lines 7–9.

The local Limine checkout is `5ed5674868183107ea4f0a42b34799af6fe8efee`.
Its `common/entry.s2.c:93` calls `disk_create_index`. The BIOS branch in
`common/drivers/disk.s2.c:244` enumerates BIOS disks; lines 294–298 read
one sector at LBA 0 into the transfer buffer and write it back. In the
optical classification expression the write is evaluated even on a
512-byte disk, because it is the left operand of the conjunction.
`disk_write_sectors` at line 146 sets the disk address packet's LBA and
count and invokes INT 13h with AX=4301h. The resulting path is Limine
probe → BIOS disk service → legacy VirtIO block OUT → raw fixture.
The ISO's extracted `limine-bios.sys` matches the local build byte for byte;
the extracted CD bootstrap differs only within the El Torito boot-info
table patched by the ISO builder. The attribution combines the boot source,
artifact comparison, pre-fixture occurrence, and successful same-sector
request. There is no captured BIOS call stack, runtime payload dump, or
request ID shared across firmware, VirtIO and the host file node.

The kernel fixture separately checks capacity and the LBA 0 marker with
a read. `kernel/src/sfs5b4_test.rs:84` writes 62, checks a flush and
reads back; line 232 submits 63 through the reset coordinator. Retry
serial lines 173 and 177 record the guest's LBA 63 request lifecycle
(VirtioLegacy incarnation 1, queue incarnation 1, generation 6, head 0,
then NORMAL_COMPLETION). Correlation to QEMU is by source, unique range
and order; the QEMU request pointer is not the guest ID. The historical
trace cannot independently separate flush at the backing boundary. The
firmware write has no partition owner: this is an unpartitioned fixture
and the request precedes the kernel and any mount.
